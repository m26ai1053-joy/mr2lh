Assume one profile per user and a DATE-typed event_date. COUNT(*) counts matched events, not distinct learners. All plans and numbers here are teaching illustrations, not captured Spark output.

Ask: does the written order of SQL dictate its execution order?
Our running example
SELECT p.city, COUNT(*) AS events
FROM activity a
JOIN profiles p
  ON a.user_id = p.user_id
WHERE a.event_date = DATE '2026-10-26'
  AND p.country = 'India'
GROUP BY p.city;

02 / Logical planning — resolve names and types

From valid syntax to meaningful operations.

What each phase establishes

Parse: recognize the query’s structure.

Analyze: resolve tables, columns and functions; check types and validity.

Optimize: rewrite the resolved tree while preserving its meaning.

Logical plans describe relational operations. They do not yet prescribe a particular join algorithm.
Same expression, more knowledge
Parsed:
  'p.city → an unresolved reference

Analyzed:
  city#12: string → a specific attribute

Optimized:
  filter each eligible input before join

Parsing can succeed; analysis fails because that column cannot be resolved.

04 / Physical planning — candidate implementations

One logical join. Different ways to execute it.

Our inner equijoin can use different physical strategies. Each must produce the same matched events.

Candidate A · Broadcast hash join
Build hash table from profiles
↓
Broadcast to activity workers
↓
Probe with activity records

Attractive when the filtered build side is small enough to distribute and hold in memory.

Candidate B · Sort-merge join
Shuffle both inputs by user_id
↓
Sort each input partition
↓
Merge matching keys

A candidate for large inputs. Existing distribution or ordering can remove some preparation work.

These are two candidate strategies, not an exhaustive list. The downstream city aggregation still has its own execution requirements.

06 / Choose algorithms and movement

“Join” is a requirement.
How to join is a decision.

One possible implementation

Suppose filtered profiles are small enough to broadcast. Build a hash table from them and distribute it to the workers processing activity.

Count locally by city, redistribute those partial counts, then combine them.

Broadcasting avoids the large-side join shuffle. Grouping by city may still require a separate shuffle.

Join choice depends on join type, statistics, hints, configuration and eligibility. Spark does not exhaustively cost every possible plan.

Illustrative physical tree · bottom → top
Final HashAggregate [city, count]
└─ Exchange [hashpartitioning(city)]
   └─ Partial HashAggregate [city, count]
      └─ BroadcastHashJoin [user_id]
         ├─ Filter + Project ← activity scan
         └─ BroadcastExchange
            └─ Filter + Project ← profiles scan

Exchange indicates redistribution. A broadcast exchange replicates data; a shuffle exchange repartitions it.

07 / Execute the chosen work efficiently

Fuse compatible operators into a tight loop.

Whole-stage code generation reduces per-row overhead inside supported execution pipelines.

Scan

Operators request rows from children. This is composable, but repeated calls and intermediate row handling can cost CPU time.

Codegen specializes a pipeline to the query. It does not remove a necessary shuffle.
Fused logic · teaching pseudocode
// A simplified filter + partial count
long count = 0;
while (input.hasNext()) {
  row = input.next();
  if (row.event_date == targetDate) {
    count++;
  }
}

Generated JVM code includes type and null handling. This snippet isolates one idea; it is not the full join query or actual generated Java.

“Whole-stage” does not mean the whole distributed query. Exchanges and unsupported operators can break fusion. Codegen stages and scheduler stages are different concepts.

Vectorization processes batches of values. It is a distinct technique that can coexist with code generation.

09 / A partition is not a promise of equal work

One oversized partition can hold up the join.

Before: uneven shuffle partitions

Illustrative sizes in MB; columns are proportional within each view.

Split the bottleneck

For an eligible skewed join, AQE can split a large shuffle partition into smaller read tasks and replicate matching input where necessary.

More tasks can share the work, at the cost of additional reading or replication.

Not a universal cure: join semantics, thresholds and available shuffle blocks constrain the split. An enormous join result remains enormous.

10 / Bring it back to production

Inspect the plan before tuning the cluster.

df.explain("extended")
# Parsed, analyzed, optimized, physical
df.explain("formatted")
# Physical outline + operator details
df.explain("cost")
# Available logical-plan statistics
df.explain("codegen")
# Generated code, where available

Four questions to take away

Read: are unnecessary columns or files being scanned?

Move: where are the exchanges, and why?

Balance: do runtime metrics show skew or spill?

Adapt: did the executed plan differ from the initial plan?

Use the SQL UI after execution to inspect runtime metrics and the final adaptive plan. EXPLAIN alone does not prove performance.
